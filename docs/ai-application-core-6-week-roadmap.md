# 银行 AI 平台项目经理 · 6 周 AI 应用工程核心路线

## 定位与目标

学习者是一名具有 Java、Spring Boot 和微服务背景的银行 AI 平台项目经理，已经完成 Python 工程基础、数据处理基础和部分真实数据分析实践。

本路线不再以“成为通用 Python 或机器学习工程师”为目标，而是聚焦：

> 能够理解 AI 应用的核心架构，独立构建和验证一个小型 AI 原型，并能从质量、安全、成本、权限、评估和工程可行性角度参与技术方案 Review。

默认主项目为“公开银行制度或产品文档问答 RAG”。它优先覆盖文档处理、检索、引用、评估、权限和幻觉风险，同时保留向模型网关、工具调用与通用助手扩展的边界。

路线持续 6 周，每周约 8–10 小时。它追求高杠杆能力，不追求 Python 数据 API、传统算法或框架的全面覆盖。

## 最重要的 20%

1. **Python 最小工程能力**：函数、容器、异常、文件、JSON、类型标注、环境变量和 pytest。
2. **数据与输入契约**：来源、粒度、缺失、重复、权限、字段含义和可追踪转换。
3. **API 与结构化输出**：HTTP、JSON、鉴权、超时、重试、错误分类和 Pydantic Schema。
4. **LLM 心智模型**：上下文、Token、采样、Prompt、幻觉、结构化输出和能力边界。
5. **RAG 核心链路**：解析、切块、Embedding、检索、上下文组装、回答与引用。
6. **AI 评估**：测试集、检索命中、回答支持度、引用、拒答和版本回归。
7. **银行场景安全治理**：数据分级、PII、权限过滤、Prompt Injection、审计和人工确认。
8. **服务化与可观测性**：FastAPI、Docker、日志、Tracing、Token、成本、延迟和版本信息。

这些能力覆盖 AI 平台项目中最常见的技术判断：应用是否需要 RAG、输入是否可用、答案是否有依据、质量如何度量、权限如何落实、失败发生在哪一层，以及原型能否稳定演示和回归验证。

## 降级为查阅或选修

| 内容 | 调整 |
| --- | --- |
| NumPy 深入与线性代数练习 | 按模型或检索概念需要时复习 |
| 大量 Pandas API、分组组合和图表变体 | 只保留一个完整数据分析闭环 |
| 传统回归与分类算法全景 | 只保留数据切分、基线、指标、过拟合和泄漏 |
| 复杂统计推导与显著性检验 | 暂缓 |
| 大量特征工程与调参 | 暂缓 |
| Python 高级数据模型与复杂生成器 | 已学内容保留，不再扩展 |
| 深入 asyncio | 先理解阻塞、超时、并发边界和何时需要异步 |
| 多种部署平台 | 只掌握本地运行与 Docker |
| Agent 框架大全 | 先掌握工具调用、状态、权限和失败边界 |
| 生产级银行系统 | 只构建公开或合成数据原型，不处理真实敏感数据 |

已有 1–5 周讲义和项目保留为历史成果与查阅资料，不再要求逐课全部完成。

## 六周路线

| 周次 | 核心主题 | 主要成果 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 数据思维收尾 + AI API 工程入口 | 带类型、异常、超时、重试和测试的模型 API 调用器 | 输入输出契约、错误路径、数据泄漏和时间边界 |
| 2 | LLM API、Prompt 与结构化输出 | 文本稳定转换为符合 Pydantic Schema 的结果 | Schema 验证、失败重试、敏感信息边界和回归用例 |
| 3 | 最小 RAG | 对公开银行文档完成带来源引用的问答 | 切块、Embedding、Top-k、上下文和引用链路 |
| 4 | RAG 评估与安全 | 至少 30 个问题的版本化评估报告 | 检索与生成分层评估、拒答、引用、注入和权限测试 |
| 5 | FastAPI、权限与工具调用 | RAG API 和一个只读模拟工具 | 输入验证、权限、超时、幂等、人工确认和测试 |
| 6 | 可观测性、Docker 与综合演示 | 可运行、可测试、可演示的银行文档 AI 助手 | 延迟、Token、成本、日志、版本、README 和风险说明 |

### 第 1 周：从数据分析过渡到 AI API

- 用一个“年份 × 季节编码”练习确认对 `groupby`、观察单位、样本量、均值和中位数的理解。
- 理解数据来源冲突、结论边界、目标泄漏、训练/验证时间切分和简单基线。
- 不再要求完成所有天气、用户类型和热力图变体，也不制作完整长篇 EDA 报告。
- 实现最小模型 API 客户端，练习 HTTP、JSON、环境变量、异常、超时、重试、类型和测试。

### 第 2 周：可靠的 LLM 调用

- 区分系统指令、用户输入和应用数据。
- 理解上下文窗口、Token、采样参数和输出不确定性。
- 使用 Pydantic 定义结构化输出契约。
- 处理超时、限流、网络错误、无效 JSON 和 Schema 不匹配。
- 建立固定输入及预期约束，执行 Prompt 回归检查。
- 记录模型、Prompt 版本、延迟和 Token 使用量。

### 第 3 周：最小 RAG 闭环

- 只使用公开或合成银行制度、产品说明文档。
- 保留来源、版本、页码或段落位置等元数据。
- 比较固定长度和按结构切块的差异。
- 生成 Embedding，建立本地向量索引并执行 Top-k 检索。
- 组装检索上下文，要求答案附带来源引用。
- 当证据不足时拒答，不让模型用常识补造银行规则。

### 第 4 周：评估、安全与治理

- 建立至少 30 个版本化问题，覆盖可回答、不可回答、歧义和对抗输入。
- 将检索问题与生成问题分开诊断。
- 检查引用是否存在，以及是否真正支持答案。
- 记录拒答、错误答案、缺失证据和回归失败。
- 测试 Prompt Injection、越权检索、敏感信息和恶意文档内容。
- 明确模型供应商、数据驻留、日志保留和人工复核边界。

### 第 5 周：API、权限和工具

- 使用 FastAPI 和 Pydantic 暴露稳定接口。
- 区分请求验证、业务错误、模型错误和依赖服务错误。
- 使用模拟身份实现最小权限过滤，不接入真实银行权限系统。
- 增加一个只读模拟工具，例如产品规则查询或确定性计算器。
- 对敏感或有副作用的工具调用要求人工确认。
- 测试正常、拒答、超时、越权和工具失败路径。

### 第 6 周：工程化交付

- 记录请求 ID、模型版本、检索文档、耗时、Token 和错误类别。
- 汇总质量、延迟和成本，不只展示单次成功案例。
- 用 Docker 打包本地服务，提供健康检查和配置说明。
- 完成 README、架构说明、评估报告、威胁模型和演示脚本。
- 明确原型到生产之间尚缺的权限、合规、容量、灾备、监控和变更流程。

## 教学方式

代码继续由课程提供完整、可运行的参考实现。目标不是从空白默写大量 Python API，而是理解为什么这样设计、每一步改变了什么，以及如何判断结果是否正确。

每个代码片段按以下顺序学习：

1. **业务问题**：解决什么实际问题？
2. **预期结构**：输入、输出、观察单位或对象分别是什么？
3. **设计思路**：为什么选择当前数据结构、API 或边界？
4. **完整代码**：提供可以直接运行的实现。
5. **逐层拆解**：解释数据流、关键语法、替代方案和工程取舍。
6. **运行验证**：使用断言、测试和输出验证，不以“没有报错”为唯一标准。
7. **小幅修改**：修改一个参数、字段、边界或失败场景并观察影响。
8. **理解复述**：说明为什么这样写、能支持什么、不能保证什么。

完整代码可以提供，但一次只引入一个主要概念，避免大段复制后直接进入下一节。

## 主项目架构

```text
公开或合成银行文档
        ↓
解析、切块与来源元数据
        ↓
Embedding 与向量检索
        ↓
权限过滤与上下文组装
        ↓
LLM 结构化回答与引用
        ↓
评估、拒答与安全测试
        ↓
FastAPI、日志与 Docker
```

可选扩展：

- **AI 平台网关**：多模型路由、配额、成本和延迟监控。
- **工具调用**：只读工具与人工确认边界。
- **通用助手**：更换知识库和系统指令，复用评估与服务框架。

## 时间分配

- 概念、架构和为什么：30%
- 运行并拆解完整代码：30%
- 小幅修改、故障实验和测试：25%
- 复盘、风险与方案 Review：15%

每周只围绕一个端到端闭环，不以看完讲义数量或掌握 API 数量作为进度指标。

## 验收标准

六周结束时，应能够独立解释并演示：

- 为什么当前问题适合或不适合使用 RAG。
- 文档怎样切块，以及切块策略如何影响召回和引用。
- 检索正确但回答错误时，应该检查哪一层。
- 如何证明 Prompt 或模型升级没有破坏旧问题。
- 哪些数据不能发送给外部模型，哪些日志不能长期保存。
- 用户是否有权检索特定文档，权限过滤应在哪个阶段执行。
- 模型何时必须拒答、降级或请求人工确认。
- 一个请求的模型、Prompt、文档版本、Token、成本、延迟和失败位置。
- 如何把原型封装为带输入契约与测试的 API。
- 什么时候应使用确定性规则、传统机器学习、检索或 LLM。

项目至少需要：

- 可从头运行的公开或合成数据原型。
- 版本化测试问题集和评估结果。
- 输入、输出、错误和权限契约。
- 正常、拒答、越权、注入、超时和依赖失败测试。
- README、架构说明、风险清单和演示说明。
- 对“原型不等于生产系统”的明确差距分析。

## 安全和使用边界

- 不将真实客户信息、内部制度或其他敏感银行数据上传到未经批准的服务。
- 学习项目只使用公开或合成内容。
- 不把脱敏当作可以自由外发的充分条件，仍需遵守组织审批和数据政策。
- 工具默认只读；有副作用的操作必须有权限校验、参数验证、审计和人工确认。
- 模型输出不能替代正式银行制度、法律意见、信贷审批或人工决策。
- 生产化建议必须单独经过安全、合规、模型风险和架构评审。

## 调整规则

- 能够解释并修改示例代码时，跳过同类 API 练习，不重复刷题。
- 运行成功但无法说明输入、输出和失败边界时，放慢节奏并增加思路拆解。
- 若 RAG 兴趣下降，可在第 4 周后切换到模型网关或工具调用，但保留评估、安全和可观测性主线。
- 时间不足时优先保留评估、安全和错误处理，减少 UI、框架和部署变体。
- 6 周不足以完成验收时，延长综合项目，不降低质量标准或扩展更多主题。
